# RequirementSeeker Agent 模块设计

## 目的与范围

本设计仅覆盖 RequirementSeeker 的 Agent 领域能力：从采集适配器提供的统一视频与评论数据中，识别可验证的软件需求机会，并提供可审计的结构化结果。

不包含：平台采集实现、Web 页面、CLI、定时调度、部署、Tag 模块及 MCP 接入。Tag 模块在产品需求中处于暂停状态；本模块不得建立依赖 Tag 扩散、权重、预算或反馈学习的不可逆数据结构。

## 已确认的设计决策

1. 采用“能力拆分优先”路线，而不是端到端原型优先或采集整合优先。
2. 先形成稳定的数据契约与离线评测样本，再接入模型调用和真实平台数据。
3. Agent 结果必须以结构化数据为主；模型自由文本只能作为可展示的说明，不能是业务准入的唯一依据。
4. 每个正式机会必须能够回溯到同一原视频及至少三位不同作者的代表性评论。
5. 在相同输入数据集、规则版本和提示词版本下，三人共识准入结果必须可重复。
6. 模型、规则和输入记录必须可审计；密钥、登录态和敏感原文不得写入普通日志或 Git。

## 模块边界

```text
采集适配器输出（模块外）
    ↓
内容标准化与去重
    ↓
评论需求信号识别
    ↓
同视频语义聚类与三人独立作者共识判定
    ↓
按需多模态上下文补充
    ↓
软件机会推导与产品过滤
    ↓
历史机会去重与证据合并
    ↓
结构化机会、推断链、模型调用审计（模块输出）
```

### 输入契约

Agent 仅依赖统一的输入记录，不直接读取 BettaFish、MindSpider 或 MediaCrawler 的内部数据库。至少需要：

- 视频：稳定 ID、平台、标题、简介、平台标签、作者、发布时间、链接与互动元数据；
- 评论：稳定 ID、所属视频 ID、作者稳定 ID、父评论 ID、正文、发布时间与互动元数据；
- 可选媒体上下文：经采集层授权提供的音频转写、关键帧、OCR 或其他可审计媒介引用；
- 执行上下文：输入记录版本、规则版本、提示词版本、模型配置引用与运行 ID。

### 输出契约

模块输出以下独立概念，供后端、前端和运行历史消费：

- `NeedSignal`：单条评论中的候选痛点、需要、替代方案或现有产品缺陷；
- `NeedCluster`：同一视频内语义一致的候选需求簇及其成员评论；
- `ConsensusDecision`：是否满足同一视频、至少三位不同作者的二元准入门槛；
- `ContextDecision`：文本上下文是否充足，是否需要或无法进行多模态处理；
- `OpportunityCandidate`：从已准入需求簇推导出的软件机会与过滤结论；
- `OpportunityMergeDecision`：新机会或与既有机会合并证据；
- `InferenceStep`：可展示的事实或 AI 推断步骤，含依据和限制；
- `ModelInvocationAudit`：模型、版本、输入记录引用、用量、结果状态、失败原因与重试信息。

## 分阶段交付策略

### 阶段 A：契约与评测基线

建立与采集实现无关的领域模型、版本策略和最小离线样本集。样本必须覆盖：有效三人共识、少于三人、三人但来自不同视频、重复作者、指代不明、非软件化需求、现有方案缺陷和无有效需求。

**完成定义：** 任何人都能在无需平台登录或模型密钥的情况下运行确定性验证，证明三人门槛和作者/视频约束没有歧义。

### 阶段 B：需求信号与共识

实现评论信号提取、同视频语义聚类和确定性三人共识判定。模型可参与语义归类，但最终准入由可检查的作者、视频和簇成员证据计算得出。

**完成定义：** 每个“通过”结果都列出视频 ID、至少三条评论 ID 和三位不同作者 ID；任何不满足约束的样本均不可创建正式机会。

### 阶段 C：上下文补充与机会推导

仅在文本不足以识别需求对象时，才请求多模态上下文。随后推导候选软件机会，并执行“可软件解决、非重运营、存在自然获客路径”的过滤。

**完成定义：** 无视觉能力或上下文仍不足时，结果明确为“上下文不足”，不以含糊评论创建机会；每个过滤结论都记录事实依据与推断依据。

### 阶段 D：去重、推断链与审计

将候选机会与历史机会比较；重复机会追加来源证据，而非新建记录。生成动态推断链和模型调用审计，使结果能在机会详情与运行详情中完整追溯。

**完成定义：** 能区分“新机会”“合并证据”“拒绝机会”“分析失败”；任何模型失败均不会产生不完整正式机会。

### 阶段 E：与运行链路集成

通过稳定接口接入采集适配器、持久化层与任务编排层，并在真实平台数据上做受预算限制的端到端验证。

**完成定义：** 一个运行可独立记录输入范围、处理量、模型调用、机会数、错误和最终状态；上游平台失败不会改变已经完成的独立平台结果。

## 横切质量要求

- **确定性：** 三人门槛不得由评论点赞、回复数或模型措辞决定。
- **可追溯：** 正式机会保留原视频和代表评论的稳定引用。
- **成本控制：** 先用本地确定性筛选缩小候选集；模型调用受预算、缓存与有限重试约束。
- **隐私与安全：** 不将 API Key、平台登录态或敏感配置写入 Git、普通日志或导出。
- **可替换性：** 采集适配器和模型供应商实现可替换，不改变领域输出契约。
- **可评测性：** 新增规则、提示词或模型版本前后都以同一离线样本集比较，不以偶发的端到端演示代替评测。

## 协作接口与责任划分

| 领域 | Agent 负责人 | 项目其他部分 |
|---|---|---|
| 领域输入/输出契约 | 定义与维护 | 按契约生产或消费 |
| 需求识别、共识、推导与去重 | 实现、测试、评测 | 提供业务反馈与验收样本 |
| 多模态触发条件与结果 | 实现、审计 | 提供模型配置与媒体访问边界 |
| 平台搜索、登录与评论抓取 | 仅定义适配接口 | 实现采集适配器 |
| 持久化、任务调度、CLI | 提供写入/调用契约 | 实现基础设施 |
| 前端展示 | 提供结构化数据与推断链 | 实现页面与交互 |

## 依赖与风险

1. Tag 模块未完成设计：Agent 首期不得依赖 Tag 相关流程或表结构。
2. 上游采集系统和平台登录态可能不稳定：离线评测必须先行，避免阻塞 Agent 核心能力。
3. 自由生成式模型会带来判断波动：准入条件必须转换为可验证的规则与证据集合。
4. 多模态调用成本高且并非总可用：必须是显式、按需的升级路径，不是默认处理步骤。
5. 初期缺少真实标注数据：先创建人工审阅的小而覆盖充分的金标集，随误判持续扩充。

## 非目标

- 自动改变 Tag 权重、扩散路径或搜索预算；
- 多模型路由、MCP Server、Hermes Skill；
- 代替用户完成可行性验证、竞品分析、需求分析或获客方案；
- 通过评分、排行榜或“强/中/弱”标签取代二元共识门槛。
