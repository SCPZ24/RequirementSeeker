# M2 数据准备完整性修复设计

日期：2026-09-24。状态：用户已认可，待按实施计划执行。关联 [Dataset Tools PR #6](https://github.com/SCPZ24/RequirementSeeker/pull/6)。

## 目标与边界

修复 PR #6 复审确认的三项问题：明示私聊账号泄漏、删除评论后仍可取得“可评测”标记，以及 Collector 未持久化精确重复数导致 M2 错误评为最高数据质量。保留现有 24 个批准视频的原始材料；未知历史计数必须如实表达，不捏造为零，也不因本修复自动重采或运行真实模型。

本设计只调整 Collector→Dataset→Agent 的必要文件契约和标注校验。HMAC 的 `kind + raw_id` 域划分、40/30/30 视频拆分、采样公式、M2 语义判断及真实评测门槛均不改变。三个包继续相互独立，通过版本化 JSON 文件交接，不添加 Python 包依赖。

## 方案选择

采用用户同意的“保留历史数据、显式未知”方案。相比强制重采全部 24 个视频，它保留当前工作；相比把缺失计数写成零，它不误导 M2 质量门。代价是同时调整三个包的契约与测试，并让历史数据最多得到降级质量评级。

### 1. Collector 采集记录

`collection.json` 增加 `collection_schema_version: "1.1"` 与 `exact_duplicate_count: 非负整数 | null`。既有三文件记录不含这两个字段，解析时视为历史版本、精确重复数未知。新记录有可信计数时写整数（包括已知的零），不能证明时写 `null`；版本与计数必须成对校验，不把缺失或 `null` 转换为零。

按 M2 既定定义，精确重复数是“相同稳定评论 ID 的额外观察数量”，而非要求 JSON 字节完全相同。只统计最终被接受的候选评论 ID：本轮原始观察中这些 ID 的额外出现，加上它们与既有同视频记录的重复出现；身份冲突被排除，不计为精确重复。采集目标选取前就被丢弃的其他 ID 不计入正式数据集。若既有生成物的历史计数未知，继续合并后的累计计数仍为未知。只有从无旧生成物的采集开始且本轮去重经过计量时，才可声明累计计数已知。`collect_from_page` 等没有可靠计量的入口写 `null`，不补猜测值。原始三文件仍保持原子发布和目录级校验，旧文件可读。

### 2. Dataset SamplingManifest 1.1

新生成的清单版本为 `1.1`，`exact_duplicate_count` 可为非负整数或 `null`。有可信计数时，`collected_total = 唯一评论数 + 精确重复观察数`；历史计数未知时，`collected_total = 唯一评论数`，明确是可观察下界而非伪装的去重前实收量。`candidate_comment_ids`、分层 ID、作者计数和规范化重复数继续由脱敏后的唯一评论计算。

Dataset 仍读取严格的批准清单和 Collector 三文件；只把 Collector 明确持久化且版本有效的计数视为已知。对已有历史原始记录输出 `exact_duplicate_count: null`，保留全部 24 个视频与评论。旧 `1.0` 清单可供迁移读取，但不得被当作“精确重复数已知”的证据。

### 3. Agent 质量判定

Agent 接受清单 `1.0` 和 `1.1`。`1.0` 一律按重复计数来源未证实处理；`1.1` 的 `exact_duplicate_count: null` 同样视为未知。未知时 `duplicate_rate` 为 `null`，不得评为 `usable`；其余完整率、页成功率、作者和层级条件满足时可评为 `degraded`，否则为 `insufficient`。已知计数的 `1.1` 清单继续按现有阈值判定，正常高质量数据仍可达到 `usable`。缺失信息不产生伪造的百分比或零值。

历史 `1.0` 清单和由历史原始文件新生成的 `1.1` 清单都不能借零重复率进入最高质量档。已有 12 视频初标和 24 视频裁决的人工门槛保持不变；降级质量不是自动获得真实模型评测资格。

### 4. 脱敏规则

在现有确定性替换顺序中扩充明示账号边界：`微信号：...`、`QQ号：...` 等与已有 `微信`、`QQ`、`wx`、`vx`、`私信` 同类的私聊账号，以及明确的 `@handle`。匹配片段替换为 `[HANDLE]`，计入替换报告；边界含糊的候选只记录不含原值的复核原因，不能因此把已命中的明示账号留在正文。邮箱先于账号处理，避免重复替换。规则版本从 `pii-v1` 递增为 `pii-v2`，旧脱敏产物不被悄悄宣称为新规则产物。测试使用合成值，不读取或输出真实账号。

### 5. 标注来源核验

`rs-dataset validate-labels <label-root> --sanitized <sanitized-root>` 必须接收对应的脱敏根目录，并按每份 `SamplingManifest` 与 `comments.jsonl` 校验视频集合、评论 ID 顺序和脱敏正文。Python 的根目录验证 API 同样要求来源路径；原有单文件结构验证 API 不单独授予可评测资格。空评论、删减/增补评论、替换正文、遗漏视频或多出视频均关闭式失败；第二标注和裁决仍必须与主标注引用完全相同的来源评论。错误只输出固定码，不回显正文。README 明确此命令变化。

既有 `labels/` 目录不自动覆盖或删除。迁移时先只读验证当前 24 份标注与对应脱敏来源一致，再通过新验证命令获得结果；若不一致，报告聚合数量和安全错误码，由操作者处理。不得以重新导出空白模板代替已填写的人工标注。

## 错误处理与回归门禁

1. Collector：旧记录解析为未知；新无历史采集写出可信零或正数；本轮重复、跨轮完全相同和身份冲突分别计量；旧记录参与增量合并后仍未知。
2. Dataset：历史记录生成 `1.1/null` 且 24 视频不丢失；可信记录生成精确数与去重前总数；未知不得变成零；CollectionRecord、SamplingManifest 与 Agent 的 JSON 互操作测试通过。
3. Agent：旧 `1.0`、新 `1.1/null` 均无法评为 `usable`，已知低重复率的 `1.1` 仍可评为 `usable`；不存在编造的重复率数值。
4. 脱敏：明示微信号、QQ号及账号型 `@handle` 的合成样本在正文、报告和标注导出中均无原值；普通语义文本与邮箱行为保持原有预期。
5. 标注：完整空表、缺一条、多一条、改正文、缺视频及跨版本来源均不能取得可评测计数；正确的 24 视频来源与独立裁决仍通过。
6. 三包分别通过完整 pytest、Ruff、strict mypy、format、锁文件与离线构建；集成测试验证 Collector 输出被 Dataset 接受、Dataset 清单被 Agent 接受；差异检查与独立复审后再讨论合并。

## 发布与真实数据

先用合成夹具做 RED→GREEN 回归，再在不修改 `.local-data/` 的前提下只读检查现有 24 视频的旧文件兼容性。本次迁移不原地覆盖当前 `sanitized/` 或 `labels/`；若要实际迁移本地副本，另行记录目标目录、输出核验和旧副本保留方式。PR #6 可为此次完整性修复包含 Collector 与 Agent 的定向契约改动，但不得借此扩展无关功能。PR #6 在三项问题修复、完整门禁与复审前保持未合并。真实模型冒烟仍等待至少 12 个视频完成初标，完整评测等待 24 个视频完成必要裁决。
