## 1. 产品概述

RequirementSeeker 是一个面向个人独立开发者的软件需求雷达。

系统每天从用户指定的少量起始 Tag 出发，在抖音和 B 站的热门视频池中进行受控扩散，分析视频评论区是否存在多人表达的共同需求。只有当同一个视频评论区内至少三位不同用户独立表达语义一致的痛点、需要或现有方案缺陷时，系统才允许创建需求机会。

AI 的职责到“发现并结构化潜在软件需求”为止。机会入库后，可行性验证、竞争分析（CA）、需求分析和获客方案均由用户在人工看板中完成。系统只提供阶段、固定检查清单、备注、链接和结论字段，不代替用户完成孵化工作，也不管理后续产品开发。

RequirementSeeker 不要求每天输出结果。没有满足条件的需求时，不创建任何机会。预计平均每十天发现一至两个需求点属于正常表现。

## 2. 背景与问题

用户在短视频平台上经常能观察到真实、可验证的软件需求。例如，视频展示了一本按小时记录活动的纸质笔记本，评论区中多位用户表达“我也想要”。虽然评论者没有明确要求软件，但这个被多人需要的纸质方案可以被抽象为一款帮助用户克服拖延的软件。

人工发现这类机会存在以下问题：

1. 需要长期浏览大量视频和评论，时间成本高。
2. 需求表达通常隐含在视频画面、口播和简短评论中，不能只靠关键词搜索。
3. 单条评论可能只是偶然想法，必须判断同一评论区内是否形成多人共识。
4. 值得关注的方向会从已有主题持续扩散，固定关键词无法覆盖意外机会。
5. 灵感如果只存在聊天记录或日报中，难以积累、去重和进行生命周期管理。
6. 需求发现之后仍需要人工完成可行性、竞品、需求和获客验证，需要一个结构化工作空间承接。

## 3. 产品目标

### 3.1 核心目标

每天自动探索抖音和 B 站热门视频评论区，将经过多人共识验证、可以被软件解决、无需重运营且具备自然获客路径的需求点沉淀为可管理的软件机会。

### 3.2 MVP 目标

1. 支持用户配置人工起始 Tag。
2. 支持从起始 Tag 自动发现关联 Tag，并以有限试探预算扩散。
3. 支持抖音和 B 站热门视频及一、二级评论采集。
4. 支持评论区需求语义聚类和三位独立用户的二元共识判定。
5. 支持在文本上下文不足时按需进行视频多模态理解。
6. 支持将真实痛点、现有非软件方案和现有产品缺陷推导为具体软件机会。
7. 只将“不依赖重运营”且“具有自然获客路径”的机会入库。
8. 支持机会去重、证据追溯和十天原始数据生命周期。
9. 支持本机定时运行、运行状态记录和手动触发。
10. 支持通过 `rs dashboard` 打开本地 Web 应用。
11. 支持新发现收件箱、机会生命周期看板、固定检查清单、Tag 管理、任务历史和本地设置。
12. 支持用户反馈影响 Tag 权重，但不建立隐式语义偏好画像。

### 3.3 非目标

MVP 不包含以下能力：

1. 不向其他用户提供 SaaS 服务，不包含注册、登录、租户、团队和权限系统。
2. 不部署云端服务，不支持公网访问和多设备同步。
3. 不主动发送邮件、Webhook、系统通知或日报。
4. 不生成 Top 3、Top 10 或固定数量的每日推荐。
5. 不为填充结果降低需求准入门槛。
6. 不自动完成可行性验证、CA、需求分析或获客方案。
7. 不管理产品开发任务、代码、版本、发布、运营和经营数据。
8. 不做全网最新视频监控，只关注平台热门池。
9. 不对需求强烈程度做强、中、弱分级。
10. 不使用多个 LLM 供应商或复杂模型路由。
11. 不在 MVP 中提供 Hermes Skill、MCP Server 或其他 Agent 集成。
12. 不做通用社媒舆情分析，也不做永久社媒数据仓库。

## 4. 用户与运行环境

### 4.1 目标用户

MVP 只有一位用户：RequirementSeeker 的拥有者，一名希望从真实用户反馈中寻找软件机会的独立开发者。

### 4.2 运行环境

1. 应用只运行在用户个人 Mac 上。
2. 后端、前端、数据库、定时任务、浏览器登录态、模型配置和采集数据均保存在本机。
3. Web 服务默认只绑定 `127.0.0.1`，不暴露到局域网或公网。
4. 用户通过命令行启动和管理应用，通过浏览器完成日常查看与人工孵化。
5. Mac 关机或休眠导致定时任务错过时，系统不自动补跑。

## 5. 核心原则

### 5.1 低频、高价值

系统宁可长时间没有新机会，也不能用低质量内容填充结果。

### 5.2 证据优先

每条正式机会必须能够追溯到一个原视频和至少三位不同用户的代表性评论。没有足够证据时不得创建机会。

### 5.3 二元共识

需求只有“达到准入条件”和“未达到准入条件”两种状态。评论数、点赞数和回复数不能被转化为需求强烈度等级。

### 5.4 人工控制方向

用户通过起始 Tag、Tag 状态和显式机会反馈控制探索方向。系统可以自动扩散，但不能自动删除人工起始 Tag，也不能从用户备注中建立黑盒偏好。

### 5.5 采集与业务解耦

BettaFish 采集能力位于独立适配器之后。RequirementSeeker 使用自己的统一数据契约、机会模型和生命周期模型，不直接以 BettaFish 内部数据库结构作为核心业务结构。

### 5.6 AI 只负责发现

AI 可以理解内容、聚类评论、判定共识、抽象需求并提出软件机会，但不能代替用户完成机会孵化和最终决策。

## 6. 核心概念

### 6.1 起始 Tag

由用户手动创建的探索起点。起始 Tag 永不因系统自动判断而休眠或删除，只能由用户手动停用。

### 6.2 扩散 Tag

由 AI 从视频标题、简介、平台 Tag、视频内容和评论中发现的关联主题。扩散 Tag 必须记录其父 Tag、发现来源、关联理由、状态和权重。

### 6.3 热门视频池

由抖音或 B 站针对指定 Tag 返回的热门排序结果。RequirementSeeker 接受平台的热门排序，不额外维护“最新视频池”。

### 6.4 疑似需求簇

同一视频评论区内，一组语义上指向相同痛点、需要、替代方案或产品缺陷的评论。在达到三位独立用户以前，它只是临时分析结果，不是正式机会。

### 6.5 软件机会

通过三人共识门槛，并经过软件化推导、非重运营过滤、自然获客路径过滤和历史去重后生成的正式记录。

### 6.6 机会孵化

用户对软件机会进行的人工开发前验证过程，包括可行性验证、竞争分析、需求分析和获客方案。孵化只提供结构与记录能力，不包含 AI 自动研究。

## 7. 总体业务流程

```text
人工起始 Tag
    ↓
为起始、活跃和试探 Tag 分配每日探索预算
    ↓
在抖音和 B 站搜索热门视频
    ↓
抓取视频元数据与评论
    ↓
文本初筛与同视频评论语义聚类
    ↓
是否有至少三位独立用户表达同一需求？
    ├── 否：保留临时数据，十天内等待增量评论
    └── 是
         ↓
    文本是否足以理解视频中的需求对象？
         ├── 是：继续
         └── 否：按需执行语音、关键帧、OCR 和多模态理解
         ↓
    推导可被软件解决的需求
         ↓
    是否不依赖重运营，并具有自然获客路径？
         ├── 否：不创建机会
         └── 是
              ↓
         与历史机会去重
              ├── 重复：追加来源证据
              └── 新机会：进入“新发现”收件箱
```

## 8. 功能需求

### FR-1 初始化与本地配置

系统应提供初始化流程，至少完成：

1. 创建本地数据目录和数据库。
2. 配置 OpenAI 兼容 API Base URL、API Key 和模型名。
3. 检测模型是否支持文本输入和图像输入。
4. 配置抖音、B 站采集登录态。
5. 创建至少一个人工起始 Tag。
6. 选择每日执行时间；默认值为当前系统时区每天 09:00。
7. 安装或提示安装本机定时任务。
8. 展示并记录上游 BettaFish、MindSpider 和 MediaCrawler 的来源及许可证。

模型密钥、平台登录态和其他敏感配置不得写入普通运行日志。

### FR-2 命令行入口

MVP 应提供统一的 `rs` 命令。至少支持：

| 命令 | 作用 |
|---|---|
| `rs init` | 初始化应用、模型、平台登录和起始 Tag |
| `rs explore` | 手动运行一次完整探测 |
| `rs schedule install` | 安装或更新每日本机定时任务 |
| `rs schedule remove` | 移除本机定时任务 |
| `rs schedule status` | 查看定时任务状态 |
| `rs status` | 查看最近运行、平台登录和模型可用状态 |
| `rs dashboard` | 启动本地后端与前端并自动打开浏览器 |

同一时刻只能运行一个探测任务。重复启动应返回现有任务状态，不得并行抓取相同数据。

### FR-3 定时探测

1. 系统每天按用户配置的本机时间触发一次探测。
2. 任务以当时的活跃 Tag、权重和预算为准。
3. 如果 Mac 在计划时间关机或休眠，任务可以被系统错过。
4. 系统恢复后不得自动补跑。
5. Dashboard 检测到当天没有成功运行时，应提示“今日探测尚未执行”，并提供手动运行入口。
6. 用户可以忽略提示，不影响历史数据和下次定时任务。
7. 每次任务必须记录开始时间、结束时间、平台结果、视频数、评论数、模型调用数、机会数、错误和最终状态。

任务状态至少包括：

- 尚未执行；
- 等待执行；
- 正在执行；
- 成功但没有发现机会；
- 成功并发现机会；
- 部分平台失败；
- 完全失败；
- 已取消；
- 登录失效，需要人工处理。

### FR-4 平台与热门池

1. MVP 支持抖音和 B 站。
2. 每个活跃 Tag 在两个平台上分别执行热门搜索。
3. 系统只使用平台热门排序结果，不建立最新视频候选池。
4. 已处理视频再次出现在热门池时，应优先增量抓取新评论。
5. 在十天原始数据保留期内，系统可以把新增评论加入已有疑似需求簇。
6. 已退出热门池的视频不主动复查。
7. 平台之间相互隔离；一个平台失败不得阻止另一个平台继续运行。

默认保守预算为：

- 每个起始或活跃 Tag、每个平台最多分析 5 个热门视频；
- 每个试探 Tag、每个平台最多分析 2 个热门视频；
- 每个视频最多保留并分析 200 条一、二级评论；
- 单次任务最多处理 50 个视频和 5,000 条评论；
- 所有预算均可在本地设置中调低或调高。

达到任何全局预算上限后，任务应正常结束并记录“预算耗尽”，不得把它标记为失败。

### FR-5 BettaFish 采集适配器

1. MVP 集成 BettaFish 的 MindSpider 及其 MediaCrawler 评论采集链路。
2. 上游模块位于独立采集适配器边界内。
3. 适配器将上游结果转换为 RequirementSeeker 的统一视频、评论、作者和运行结果数据契约。
4. RequirementSeeker 的需求发现流程不得直接查询上游专用业务表。
5. 适配器应支持：
   - 按 Tag 搜索热门视频；
   - 获取视频标题、简介、平台 Tag、作者、发布时间、链接和互动元数据；
   - 获取一级和二级评论；
   - 获取稳定的视频 ID、评论 ID 和作者 ID；
   - 保存和检查平台登录态；
   - 报告验证码、登录失效、限流和页面结构变化。
6. 无法获得稳定作者 ID 的评论可以保留用于上下文，但不能计入“三位不同用户”门槛。
7. 采集适配器不可用时，Dashboard 和人工机会看板仍应正常工作。

### FR-6 Tag 图谱与扩散（待重新设计，暂停实现与验收）

> 本节为历史方向草案，不是当前定稿需求。

Tag 状态至少包括：

- `seed`：人工起始 Tag；
- `trial`：自动发现、正在试探的 Tag；
- `active`：试探后继续探索的扩散 Tag；
- `sleeping`：暂时不再自动探索；
- `disabled`：用户手动停用。

业务规则：

1. 用户可以创建、编辑、置顶、停用和恢复起始 Tag。
2. AI 可以从已分析视频的标题、简介、平台 Tag、内容和评论中提出扩散 Tag。
3. 每个扩散 Tag 必须记录：
   - 父 Tag；
   - 来源视频；
   - 发现时间；
   - 关联理由；
   - 当前状态；
   - 当前权重；
   - 已执行次数；
   - 产生的疑似需求簇和正式机会数量。
4. 新扩散 Tag 自动进入 `trial`，无需人工批准。
5. `trial` Tag 默认在十天内获得最多三次成功探索机会，并使用较小视频预算。
6. 如果试探期间产生至少一个包含两位不同用户的疑似需求簇，或产生正式机会，则 Tag 晋升为 `active`。
7. 如果三次成功探索后没有产生上述结果，则 Tag 自动进入 `sleeping`。
8. 起始 Tag 不受自动休眠规则影响。
9. 用户可以随时将 `trial`、`active` 或 `sleeping` Tag 手动设为任意允许状态。
10. 自动扩散必须受全局 Tag 数量、每次新增 Tag 数量、层级深度和任务预算约束，避免无限扩散。
11. 默认每个父 Tag 每次运行最多新增三个 `trial` Tag；单条扩散路径默认最大深度为三层。
12. 达到深度上限后，新 Tag 只进入待查看列表，不自动获得探索预算；用户可手动启用。

### FR-7 Tag 权重反馈（待重新设计，暂停实现与验收）

> 本节为历史方向草案，不是当前定稿需求。

机会反馈只影响 Tag 权重，不训练或生成语义偏好画像。

默认规则：

1. 机会从“新发现”进入“感兴趣”时，提高来源 Tag 和其直接父 Tag 的权重。
2. 机会从“新发现”直接进入“放弃”时，降低来源 Tag 权重。
3. 机会进入“决定开发”时，再次提高来源 Tag 和其直接父 Tag 的权重。
4. “暂缓”不改变权重。
5. “重复”只执行证据合并，不改变权重。
6. 权重变化必须记录原因、时间、关联机会和变化前后数值。
7. 权重只影响有限探索预算的分配顺序，不改变需求三人门槛。
8. 权重不得使人工起始 Tag 自动休眠或删除。
9. 用户可以查看并手动调整权重。

### FR-8 评论预处理与独立用户判定

在调用需求分析前，系统应执行确定性预处理：

1. 使用平台和评论 ID 去重。
2. 使用平台和稳定作者 ID 判断不同用户。
3. 同一作者的多条相似评论只能计为一位用户。
4. 作者自己的评论不能计入需求共识，但可作为视频上下文。
5. 纯表情、无意义附和、抽奖、广告、引流和明显机器人内容不得计入共识。
6. 点赞、收藏、转发和只有点赞没有评论的用户不得计入共识人数。
7. 一级评论和二级回复都可以参与共识，只要来自不同用户并明确表达相关需要。
8. 预处理规则的版本应随分析结果记录，以便未来复查。

### FR-9 需求语义聚类与共识门槛

1. 需求聚类只能在同一个视频评论区内完成。
2. 跨视频出现的相似评论不能共同凑足三人门槛。
3. 同一评论区内，至少三位不同用户分别表达语义一致的痛点、需要、现有方案需求或产品缺陷时，疑似需求簇才通过共识门槛。
4. 三人门槛是固定二元规则，不根据视频热度、评论总量或点赞量动态变化。
5. 达到三人门槛后，不输出“强烈、中等、微弱”等需求强度。
6. 如果 AI 无法稳定判断三条评论是否语义一致，应判定为未通过，而不是降低门槛。
7. 未通过门槛的疑似需求簇在十天内保留，允许新增评论加入。
8. 达到门槛后，应选择至少三条来自不同用户、能够独立支撑结论的代表性评论作为证据。

### FR-10 分层视频理解

第一层分析始终执行，输入包括：

- 视频标题；
- 视频简介；
- 平台 Tag；
- 评论正文；
- 评论回复关系；
- 必要互动元数据。

只有同时满足以下条件时，才触发第二层多模态分析：

1. 已存在达到三人门槛的评论簇；
2. 评论包含“这个、同款、也想要、求链接、怎么做”等依赖视频上下文的指代，或需求对象不明确；
3. 标题和简介不足以可靠还原需求对象。

第二层可以按实现能力组合使用：

- 平台字幕或语音转写；
- 关键帧抽取；
- 画面 OCR；
- 支持图像输入的 OpenAI 兼容模型。

如果配置模型不支持图像，或第二层处理后仍不能明确需求对象，则：

1. 不创建软件机会；
2. 将该需求簇标记为“上下文不足”；
3. 在十天保留期内允许用户查看运行记录和手动重试；
4. 不用猜测性描述填补缺失信息。

### FR-11 软件机会推导

AI 应识别并处理三类输入：

1. 显式软件诉求，例如“有没有这样的 App”；
2. 可以软件化的现有方案，例如纸质本、Excel、模板、卡片或手工工作流；
3. 重复痛点和现有产品缺陷，例如“现在这样做太麻烦”或“现有 App 缺少某项关键能力”。

每个通过共识的需求簇必须被推导为一个足够具体的软件机会。推导结果至少回答：

1. 谁在什么场景下遇到什么问题；
2. 用户当前使用什么方案或为什么没有可用方案；
3. 软件可以提供什么核心行为或结果；
4. 最小有价值的软件形态是什么；
5. 为什么该方案不依赖重运营；
6. 第一批用户可以从哪里自然获取。

纯宏观抱怨、无法落到软件行为的问题、需要持续人工服务才能交付价值的方案，以及无法指出具体自然获客路径的方案不得入库。

### FR-12 两项硬过滤条件

正式机会必须同时满足：

#### 1. 不依赖重运营

核心价值主要由软件自动交付。机会不得要求开发者长期承担以下工作才能成立：

- 人工咨询或审核；
- 一对一交付；
- 高频内容生产；
- 社群维护；
- 线下履约；
- 其他与用户增长近似线性增加的人力服务。

#### 2. 具有自然获客路径

机会必须指出至少一个可执行的首批用户来源，例如：

- 原始视频评论区；
- 相关 Tag 的内容人群；
- 展示同类痛点的创作者；
- 用户自己的内容账号可发布的演示主题；
- 其他与需求证据直接相关、可自然触达的渠道。

“投广告”“做 SEO”“发社交媒体”这类没有对象和内容角度的泛化描述不算明确获客路径。

其他因素，如开发周期、付费可能、竞争程度和技术难度，只作为机会说明，不是 MVP 的一票否决条件。

### FR-13 机会去重与证据合并

1. 新机会入库前必须与历史机会做语义去重。
2. 去重可以跨视频、跨平台和跨时间进行。
3. 如果新需求簇与已有机会属于同一用户问题和同一软件解法方向，不创建第二张机会卡，而是把新视频和评论作为额外来源追加到主机会。
4. 证据增加不得被解释为需求强度升级。
5. 如果两个机会只有表面词汇相近，但目标用户、场景或核心结果不同，应保留为独立机会。
6. 用户可以手动将两个机会标记为重复并选择主机会。
7. 合并操作必须可追溯，且不得删除原始来源关系。

### FR-14 正式机会数据

每条正式机会至少包含：

- 唯一 ID；
- 机会标题；
- 一句话需求摘要；
- 目标用户；
- 使用场景；
- 用户痛点或想要的结果；
- 当前方案、实物、手工流程或现有产品缺陷；
- 建议的软件形态；
- 核心价值与最小功能描述；
- 不依赖重运营的理由；
- 自然获客路径；
- 主要不确定性和风险；
- 来源平台；
- 原视频 ID、标题、作者、链接和必要上下文；
- 至少三条不同用户的代表性评论；
- 起始 Tag、完整扩散路径和命中 Tag；
- 首次发现时间和最近补充证据时间；
- 模型名、提示词版本和分析规则版本；
- 生命周期阶段；
- 用户备注、相关链接和各阶段检查清单；
- 重复关系和合并来源。

正式机会不包含需求强度等级，也不包含 Top 排名。

### FR-15 新发现收件箱

1. 新生成的独立机会进入“新发现”收件箱。
2. 收件箱按首次发现时间排序，不设置每日 Top 数量。
3. 没有新机会时显示空状态，不生成占位内容。
4. 用户可以从收件箱执行：
   - 标记感兴趣；
   - 直接放弃；
   - 暂缓；
   - 标记重复并关联主机会；
   - 查看完整证据；
   - 添加备注和链接。
5. 查看机会不等于改变其生命周期状态。

### FR-16 人工孵化看板

生命周期阶段为：

```text
新发现
→ 感兴趣
→ 可行性验证
→ CA
→ 需求分析
→ 获客方案
→ 决策就绪
→ 决定开发
```

以下结果可以从人工阶段进入：

- 暂缓；
- 放弃。

“重复”是机会关系，不是普通生命周期阶段。

业务规则：

1. 只有“新发现”由 AI 创建。
2. 从“感兴趣”开始，所有阶段均由用户手动推进。
3. 系统不得自动完成检查项、生成阶段结论或推进状态。
4. 每个阶段提供固定检查清单、专属备注、参考链接和阶段结论。
5. 用户可以返回前一阶段补充信息。
6. 用户可以从暂缓状态恢复到原阶段。
7. “决定开发”是 RequirementSeeker 管理范围的终点。

### FR-17 固定检查清单

#### 可行性验证

- [ ] 原始评论是否代表一个可复现的真实场景
- [ ] 问题是否适合由软件解决
- [ ] 软件是否可以独立交付核心价值
- [ ] 是否存在难以获取的数据、平台权限或外部资源
- [ ] 是否存在关键技术或合规阻碍
- [ ] 是否仍然满足“不依赖重运营”
- [ ] 可行性阶段结论已填写

#### CA

- [ ] 已记录直接竞品
- [ ] 已记录间接替代方案
- [ ] 已整理现有方案的主要缺陷
- [ ] 已找到可切入的细分场景或差异点
- [ ] 已判断市场拥挤程度
- [ ] CA 阶段结论已填写

#### 需求分析

- [ ] 已定义目标用户
- [ ] 已定义核心使用场景
- [ ] 已定义用户希望获得的结果
- [ ] 已列出 MVP 必须具备的功能
- [ ] 已列出 MVP 明确不做的功能
- [ ] 已记录关键假设和验证方法
- [ ] 需求分析阶段结论已填写

#### 获客方案

- [ ] 已记录原始需求来源
- [ ] 已定义第一批可触达用户
- [ ] 已选择首批获客渠道
- [ ] 已定义适合发布的内容或演示角度
- [ ] 已定义首轮需求验证动作
- [ ] 已确认方案仍然属于自然获客
- [ ] 获客阶段结论已填写

#### 决策就绪

- [ ] 四个阶段的结论均已完成
- [ ] 关键风险和未验证假设已列出
- [ ] 已做出“决定开发、暂缓或放弃”的选择

### FR-18 Dashboard 功能范围

本地 Web 应用的当前页面清单、布局和交互以 `docs/Pages.md` 为准。以下列表保留业务能力索引：

1. **概览**
   - 今日任务状态；
   - 最近一次成功任务；
   - 平台登录状态；
   - 模型状态；
   - 新发现机会数量；
   - 即将清理的原始数据数量；
   - 手动运行入口。
2. **新发现收件箱**
   - 查看新机会；
   - 查看证据；
   - 执行初步反馈。
3. **机会看板**
   - 按生命周期查看机会；
   - 手动移动阶段；
   - 填写检查清单、备注、链接和结论。
4. **机会详情**
   - 查看需求、软件化推导、硬过滤理由；
   - 查看原视频文字上下文、原页面外链与代表性评论；
   - 不在 Web 端展示视频、缩略图或播放器；
   - 查看阶段历史和重复关系。
5. **Tag 管理（待重新设计）**
   - 当前不提供 Tags 导航或管理页面；
   - 完成独立需求脑暴后再补充页面、状态和交互。
6. **任务历史与运行详情**
   - 查看每次探测的状态、统计、错误和预算使用；
   - 区分正常零结果与失败；
   - 对允许重试的失败执行手动重试。
7. **设置**
   - 模型配置；
   - 平台登录状态；
   - 调度时间；
   - 采集预算；
   - 十天数据保留策略；
   - 上游来源和许可证。

机会和任务历史应支持基本搜索与过滤。Tag 的搜索、筛选和管理规则待重新设计。

### FR-19 单一模型配置

1. MVP 只配置一个 OpenAI 兼容模型。
2. 配置项包括 API Base URL、API Key 和模型名。
3. 同一个模型用于评论理解、语义聚类、共识判断、需求抽象、软件机会推导和按需图像理解。
4. 系统启动时应检测文本能力；检测失败时不得启动 AI 分析任务。
5. 系统应检测图像能力；检测失败时允许文本流程运行，但必须禁用需要视觉上下文的机会生成。
6. 模型输出必须经过结构化 Schema 校验；不符合 Schema 时进行有限次数修复或重试。
7. 每次分析记录模型名、提示词版本、输入记录 ID、结果和错误，但不得把 API Key 写入记录。
8. Dashboard 应展示调用次数、失败次数和可获得的 Token 使用量。

### FR-20 数据生命周期

#### 普通原始数据

以下数据保留十天：

- 普通视频元数据；
- 评论正文；
- 回复关系；
- 临时语义簇；
- 未达三人门槛的疑似需求；
- 多模态分析中间结果。

到期后执行自动清理。

#### 长期去重数据

以下数据长期保留：

- 平台和视频 ID；
- 平台和评论 ID；
- 作者匿名哈希；
- 内容哈希；
- 首次和最后处理时间；
- 处理结果状态；
- 必要的增量抓取游标。

长期去重数据不得包含普通评论的可读正文。

#### 正式机会证据

形成正式机会后，以下数据永久保留：

- 机会结构化内容；
- 原视频必要上下文和链接；
- 至少三条代表性评论；
- 证据作者匿名标识；
- Tag 来源路径；
- 用户人工孵化内容；
- 重复和合并关系；
- 分析与状态审计记录。

清理任务不得删除正式机会引用的证据。

### FR-21 上游来源与许可证展示

1. Web 首页必须标明评论采集能力来源于以下上游项目，并提供可点击链接：
   - BettaFish：`https://github.com/666ghj/BettaFish`
   - MindSpider：`https://github.com/666ghj/BettaFish/tree/main/MindSpider`
   - MediaCrawler：`https://github.com/NanmiCoder/MediaCrawler`
2. README 必须说明实际复用范围和上游地址。
3. 源码或安装包中必须保留上游要求的版权和许可证文件。
4. 上游代码与 RequirementSeeker 自有代码应在目录或依赖关系上可识别。
5. 设置页应提供完整许可证查看入口。
6. 来源展示不得暗示 BettaFish 或 MediaCrawler 作者为 RequirementSeeker 提供担保或背书。

## 9. 数据与状态要求

### 9.1 主要实体

系统至少需要以下业务实体：

- `PlatformAccount`：平台及本地登录状态；
- `Tag`：起始或扩散 Tag；
- `TagEdge`：Tag 父子关系和扩散来源；
- `ExplorationRun`：一次探测任务；
- `CrawlResult`：平台或 Tag 的采集结果；
- `Video`：十天内保留的视频原始数据；
- `Comment`：十天内保留的评论原始数据；
- `ContentFingerprint`：长期去重指纹；
- `DemandCluster`：临时疑似需求簇；
- `Opportunity`：正式软件机会；
- `OpportunityEvidence`：视频和代表性评论证据；
- `OpportunityRelation`：重复和主机会关系；
- `LifecycleTransition`：人工阶段变更记录；
- `StageChecklist`：固定检查项及完成状态；
- `StageNote`：阶段备注、链接和结论；
- `TagWeightEvent`：显式反馈引起的权重变化；
- `ModelInvocation`：模型调用审计和用量。

### 9.2 幂等性

1. 相同平台和视频 ID 不得重复创建视频。
2. 相同平台和评论 ID 不得重复创建评论或重复计入共识。
3. 同一个探测任务因进程重启而恢复时，不得重复创建机会。
4. 重复运行相同数据集必须得到相同的三人门槛结果；模型推导文本允许措辞不同，但准入证据必须一致。

### 9.3 审计

以下操作必须记录：

- 机会创建；
- 机会合并；
- 生命周期变更；
- 暂缓、恢复和放弃；
- 检查项修改；
- Tag 创建、扩散、休眠、恢复和权重变化；
- 定时任务安装、修改和移除；
- 原始数据清理；
- 模型和平台错误。

## 10. 异常与恢复

### 10.1 平台登录失效

1. 当前平台停止采集并标记“登录失效”。
2. 另一个平台继续运行。
3. Dashboard 显示需要重新登录。
4. 系统不得无限重试扫码、验证码或登录操作。

### 10.2 平台限流或结构变化

1. 执行有限退避重试。
2. 达到重试上限后记录失败。
3. 保留已成功采集的数据。
4. 不将部分采集误报为完整成功。

### 10.3 模型失败

1. 网络和临时服务错误执行有限重试。
2. 结构化输出错误执行有限修复。
3. 达到上限后保留待处理状态。
4. 不因模型失败创建不完整机会。

### 10.4 多模态能力不足

需要画面上下文但模型不支持视觉时，需求簇保持“上下文不足”，不得仅根据“我也想要”等指代性评论创建机会。

### 10.5 应用或任务崩溃

1. 任务状态标记为失败或中断。
2. 已完成阶段的数据安全提交。
3. 下次任务依靠幂等键跳过已处理记录。
4. 系统不自动补跑错过的每日任务。

### 10.6 数据清理失败

清理失败不得删除正式机会证据。系统记录错误，并在下一次正常维护周期重试。

## 11. 非功能需求

### 11.1 本地安全

1. Web 服务默认仅监听 `127.0.0.1`。
2. API Key、平台 Cookie 和浏览器登录态只能保存在用户本机。
3. 敏感信息不得进入 Git、普通日志、机会导出或模型审计正文。
4. 本地敏感配置应使用操作系统安全存储或权限受限文件。

### 11.2 可维护性

1. 采集、分析、机会业务、生命周期、调度和 Web API 必须具有明确边界。
2. BettaFish 适配器可以被替换，而不改变机会和看板数据结构。
3. 提示词和结构化输出 Schema 必须版本化。
4. 固定业务规则优先使用确定性代码，不依赖 LLM 猜测。

### 11.3 可观察性

用户必须能够回答：

- 今天任务是否运行；
- 哪个平台成功或失败；
- 分析了多少 Tag、视频和评论；
- 为什么没有产生机会；
- 哪一步消耗了模型调用；
- 哪些数据将在十天后清理；
- 哪个反馈改变了 Tag 权重。

### 11.4 数据完整性

1. 机会证据和人工孵化数据必须使用事务性存储。
2. 清理普通原始数据不得破坏机会引用。
3. 用户备注和阶段结论不得因重新分析机会而被覆盖。

### 11.5 性能与成本

1. 所有采集和模型调用受可配置预算控制。
2. 文本足够时不得触发多模态处理。
3. 已处理评论通过 ID 和哈希避免重复调用模型。
4. 达到预算属于正常受控结束，不属于错误。

## 12. 验收标准

### AC-1 正常零结果

给定一次成功的抖音和 B 站探测，如果没有任何评论簇达到三位独立用户门槛，则：

- 不创建机会；
- 任务状态为“成功但没有发现机会”；
- Dashboard 不显示伪造推荐。

### AC-2 三人共识

给定同一视频下三位不同用户表达同一需求，且评论通过预处理，则系统可以进入需求推导；两位用户、同一用户三条评论或只有大量点赞均不得通过。

### AC-3 不跨视频凑门槛

三个不同视频各有一位用户表达同一需求时，不得形成三人共识。

### AC-4 视频上下文

当三条评论仅表达“我也想要”，标题和简介无法说明对象时，系统必须触发第二层上下文分析。第二层失败时不得创建机会。

### AC-5 软件化推导

当视频展示非软件方案且评论形成共识时，系统能够把核心用户结果抽象为具体的软件机会，而不是只复述“用户想要这个产品”。

### AC-6 两项硬过滤

缺少“不依赖重运营”的合理说明，或缺少具体自然获客路径时，需求簇不得成为正式机会。

### AC-7 不做强度分级

正式机会及 Dashboard 中不得出现基于评论数、点赞数或互动量生成的需求强、中、弱等级。

### AC-8 不做固定排名

系统不得生成每日 Top 3 或为了固定数量重复、补齐机会。新需求有多少入库多少。

### AC-9 跨日累计

某视频第一天有两位用户表达同一需求、十天保留期内出现第三位用户时，系统可以让原疑似需求簇通过门槛。

### AC-10 十天清理

普通原始视频、评论和未成立疑似需求到期后被清理；去重指纹继续存在；正式机会引用的代表性证据不被清理。

### AC-11 Tag 试探（暂停验收）

本验收项等待 Tag 模块重新设计。以下旧规则仅保留为历史记录：扩散 Tag 自动获得有限试探预算；达到晋升条件后成为活跃 Tag；三次成功试探均无有效信号时自动休眠；起始 Tag 不自动休眠。

### AC-12 反馈只影响 Tag 权重（暂停验收）

本验收项等待 Tag 模块重新设计。以下旧规则仅保留为历史记录：标记感兴趣、放弃或决定开发时，系统按规则记录 Tag 权重变化；备注内容不得被自动解析成偏好；权重变化不得改变三人门槛。

### AC-13 错过任务

Mac 在计划时间休眠导致任务未运行时，系统恢复后不自动补跑；打开 Dashboard 时显示提示，并允许手动探测。

### AC-14 平台隔离

抖音采集失败而 B 站成功时，任务状态为“部分平台失败”，B 站数据正常进入分析流程。

### AC-15 人工孵化

系统不得自动勾选检查项、填写阶段结论或推进看板。用户能够手动完成四个孵化阶段并最终选择决定开发、暂缓或放弃。

### AC-16 本地运行

`rs dashboard` 能启动本地前后端并打开浏览器；服务默认不能从其他设备访问。

### AC-17 来源展示

Web 首页、README 和许可证入口能够识别实际使用的 BettaFish、MindSpider 和 MediaCrawler 来源及许可信息。

## 13. MVP 成功判断

MVP 的成功不以每天产生机会数量衡量。以下条件同时满足时，视为产品假设得到初步验证：

1. 系统可以连续执行十天以上的本机定时探测，并准确区分零结果和失败。
2. 所有正式机会均具有一个原视频和至少三位独立用户的可追溯评论证据。
3. 系统能够至少一次从隐式、非软件表达中推导出具体软件机会。
4. 用户人工审阅后，正式机会没有明显违反“不依赖重运营”和“自然获客”两项硬条件。
5. Tag 相关成功标准等待独立需求脑暴完成，当前不参与 MVP 成功判断。
6. 用户可以用 Dashboard 将机会从新发现推进到决策结论。
7. 普通原始数据能够按十天策略清理，且不破坏机会证据。

平均十天出现一至两个机会是产品预估，不是必须达到的输出配额。

## 14. MVP 后扩展

MVP 稳定后，可以在不改变核心业务模型的前提下增加 MCP Server，供 Hermes 或其他 Agent 使用。候选能力包括：

- 查询未读新机会；
- 搜索历史机会；
- 获取单个机会及证据；
- 查看和修改生命周期状态；
- 读取和更新人工检查清单；
- 查询、创建、启用和停用 Tag；
- 查看最近任务状态；
- 手动触发一次探测。

MCP 不属于 MVP 验收范围，MVP 也不得依赖 MCP 才能完成任何核心业务。

## 15. 已确认的关键决策

| 主题 | 决策 |
|---|---|
| 使用对象 | 仅供用户本人使用 |
| 运行位置 | 个人 Mac，本机 localhost |
| 产品形态 | 独立全栈应用，前后端分离 |
| 调度 | 应用自行安装和管理每日本机定时任务 |
| 漏跑 | 不自动补跑，Dashboard 提醒并允许手动运行 |
| 平台 | 抖音和 B 站 |
| 视频范围 | 只关注平台热门池 |
| 探索起点 | 历史方向为人工起始 Tag，待 Tag 模块重新设计 |
| 扩散 | 历史方向为有限试探，待 Tag 模块重新设计 |
| 反馈学习 | 历史方向为只调整 Tag 权重，待 Tag 模块重新设计 |
| 共识规则 | 同一视频、至少三位不同用户、二元门槛 |
| 需求范围 | 显式软件诉求、可软件化现有方案、重复痛点和产品缺陷 |
| 视频理解 | 文本优先，必要时按需多模态 |
| 模型 | 单一 OpenAI 兼容模型 |
| 入库方式 | 有合格需求就入库，没有就不入库 |
| 排名 | 不做 Top 3 或固定推荐数量 |
| 硬过滤 | 不依赖重运营；具有自然获客路径 |
| 原始数据 | 分层保留，普通原始数据十天后清理 |
| 孵化 | 人工看板，不使用 AI 完成孵化业务 |
| 孵化阶段 | 可行性、CA、需求分析、获客方案 |
| 采集实现 | 集成完整 BettaFish/MindSpider/MediaCrawler 链路 |
| 来源说明 | Web 首页、README 和许可证入口展示 |
| 主动推送 | MVP 不做 |
| Agent 接入 | MVP 后再提供 MCP |
